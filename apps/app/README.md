## 아키텍처 방향

기존 계획(RN 전체 재구현)에서 **웹뷰 기반으로 전환**. `apps/web`(Next.js, 이미 배포된 실서비스)을 `react-native-webview`로 그대로 감싸서 화면 대부분을 재사용하고, 네이티브에서만 가능한 기능(문자 인식 등)만 RN 네이티브 모듈로 추가하는 하이브리드 구조.

- Capacitor 스파이크도 잠깐 검토했으나 최종적으로 **RN(Expo) + WebView**로 결정 — 최초 기획(이 폴더의 예정 스택)과 일치하고, 실기기 테스트도 Expo Go로 바로 가능해 진입장벽이 낮음
- BE에 이미 추가된 better-auth `oneTimeToken` 플러그인(세션 쿠키 교환용)은 이 구조에서도 그대로 재사용

## 핵심 기능 — AI 문자 인식 자동 가계부 입력 (Android 전용)

**목적**: 카드 결제 알림 문자를 앱이 자동으로 인식해 가계부에 지출 항목을 자동 생성

- **Android만 지원** — iOS는 서드파티 앱의 SMS 접근 자체가 OS 정책상 불가능 (하드 제약). iOS는 다음 단계에서 수동 입력 등 대체 방식으로 별도 검토
- **은행 실시간 연동(오픈뱅킹)은 범위 밖** — 개인 프로젝트로는 사업자 등록·심사가 필요해 지금 단계에서 불가능. 문자 알림 파싱만으로도 은행 제휴 없이 "자동 기록" 목표는 달성 가능
- 파싱: 은행/카드사 알림 문자는 정형화된 포맷이라 정규식으로 금액/날짜/가맹점명 추출
- AI 역할: 가맹점명 → 지출 카테고리 자동 분류(예: "스타벅스" → 카페) — 문자 "인식" 자체보다 이 분류 단계에서 LLM 활용이 핵심
- Google Play에 공개 배포할 경우 SMS 권한 심사(코어 기능 소명)가 필요하나, 개인용으로만 쓸 경우 해당 없음
- 이 기능이 들어가면 Expo Go로는 테스트 불가 (커스텀 dev client 필요) — EAS Build로 로컬 Android Studio 없이 빌드 가능

## 로그인 (구글 OAuth) — 쿠키 교환 방식

시스템 브라우저(`expo-web-browser`)에서 구글 로그인 → BE `oneTimeToken` 플러그인으로 일회성 코드 발급 → 커스텀 스킴 딥링크(`expo-linking`)로 앱 복귀 → 앱의 WebView 자신이 그 코드를 검증 요청해 세션 쿠키를 직접 심음. 임베디드 웹뷰에서는 구글 OAuth 로그인 자체가 차단되기 때문에, 로그인만 시스템 브라우저로 분리하고 세션을 코드 교환으로 되돌려주는 구조.

## 예정 기술 스택

| 항목 | 기술 |
|------|------|
| 프레임워크 | React Native (Expo, 관리형) |
| 웹뷰 | react-native-webview (배포된 Next.js URL 로드) |
| 로그인 브라우저 | expo-web-browser |
| 딥링크 | expo-linking |
| 문자 인식 (Android) | 네이티브 모듈 (예: react-native-android-sms-listener 또는 커스텀 모듈) |
| 상태관리 | Zustand 또는 Jotai (웹뷰 밖 네이티브 화면용) |
| 빌드 | EAS Build (커스텀 dev client — 문자 인식 기능 포함 시 필수) |
| 배포 | Google Play 우선, App Store는 다음 단계 |
