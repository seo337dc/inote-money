# FSD 아키텍처 피드백 — 외부 과제 회고

> 출처: `langdy-fe-assignment` (별도 사이드 프로젝트, 프론트엔드 채용 과제) 탈락 피드백.
> `inote-money`는 FSD 구조를 그대로 쓰고 있진 않지만, 레이어형 아키텍처를 다룰 때 반복될 수 있는 문제라 여기 남겨둠.

## 평가자 피드백 요약

- FSD 폴더 이름(entities/features/widgets/shared)만 가져다 썼을 뿐, 레이어 간 **책임 분리**가 명확하지 않았음
- **Entity 간 참조 관계** 기준이 불명확 — 어떤 entity가 어떤 entity를 참조해도 되는지 규칙이 없었음
- 레이어 간 **의존성 방향** 위반이 일부 확인됨 (상위→하위만 참조해야 하는데 역참조 발생)
- 무엇보다 "왜 이 아키텍처를 골랐고, 왜 이렇게 나눴는지"에 대한 **일관된 설계 원칙·의사결정 근거**가 드러나지 않음
- AI 활용 자체는 긍정 평가. 다만 AI 결과물을 그대로 쓴 수준을 넘어 아키텍처에 맞게 **의도적으로 다듬은 흔적**은 부족했다고 지적

## 원인 분석

- 렌더링 전략 같은 결정은 PR 문서에 기록했지만, **레이어 의존성 방향을 코드 레벨에서 강제하는 장치**(lint 룰 등)가 없어서 규칙이 지켜지는지 확인할 방법이 없었음
- "폴더를 FSD 이름대로 만든다" ≠ "FSD 원칙을 적용한다" — 이 둘을 같다고 착각하기 쉬움

## 개선점 (다음 프로젝트 적용)

- [ ] 레이어 구조를 쓸 때 의존성 방향을 문서에만 적지 말고 **lint 룰로 강제** 검토 (예: `eslint-plugin-boundaries` 또는 import 경로 규칙)
- [ ] 새 모듈을 어느 레이어에 둘지 정할 때 "왜 여기 두는지" 한 줄이라도 PR/커밋에 남기기 — 사후 총정리가 아니라 **그때그때** 기록
- [ ] entity 간 참조가 필요하면 그 관계를 명시적으로 정의 (어떤 entity가 어떤 entity를 참조 가능한지)
- [ ] 아키텍처를 "형식(폴더명)"이 아니라 "원칙(의존성 방향+책임 분리)"으로 설명할 수 있는지 스스로 점검

## inote-money에 적용할 부분

- 현재 레포 구조(`apps/web`, `backend`, `packages`)는 FSD는 아니지만, 앞으로 도메인이 늘어나면서 계층을 나누게 되면 위 개선점을 먼저 적용
- 특히 `packages/` 공통 모듈과 `apps/web` 사이의 의존성 방향은 지금부터 규칙을 정해두는 게 좋음
